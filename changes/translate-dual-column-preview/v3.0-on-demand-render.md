## 1. 触发：用户反馈

> **「原文和译文应该是相同的格式也就说DOCX格式那么我们是用图片+文字显示的」**

v2.0 把右栏做成了"合成文本页"（`TextPage` 组件 + `<p>` 标签），但这跟左栏的"PDF 图+文字层"在视觉上是两种不同的东西 — 左栏像真文档，右栏像网页。

v3.0 让右栏也走 **DOCX→PDF→PDFium 真实渲染管线**，与左栏使用**完全相同的格式**（PDF 页面图 + PDFium 文字层 spans）。

> v3.0 关键决策（用户通过 AskUserQuestion 确认）：
> - **右栏渲染方案**：生成译文 DOCX → soffice 转 PDF → PDFium 栅格化（推荐）
> - **触发时机**：按需渲染，用户滚动到某页时再生成（推荐）

## 4. 关键设计决策

### 4.1 为什么用 in-flight Promise 去重？

前端同时拉取 `/render-image` 和 `/render-text`，两个 handler 独立调用 `renderTranslatedPage()`。如果不加锁：

```
T0: image handler → soffice 转换 → 写 tmp_aaa.html → tmp_aaa.pdf → rasterize
T0: text handler  → soffice 转换 → 写 tmp_bbb.html → tmp_bbb.pdf → extract
                  ^^^^^^^^ 同样写 cachePng 互相覆盖
```

并发会触发两次 soffice 转换，且共享的 `cachePng`/`cacheHtml` 文件被两个 worker 互相覆盖（"soffice did not produce PDF" 错误）。

解决：用 `inflightRenders: Map<key, Promise>` 缓存同 key 的渲染 Promise，第二个 await 复用第一个的结果：

```js
if (inflightRenders.has(key)) return await inflightRenders.get(key)
const p = doRender(...)
inflightRenders.set(key, p)
try { return await p } finally { inflightRenders.delete(key) }
```

### 4.2 为什么用 150 DPI 而非 96？

- 96 DPI = 794×1123（A4 @ 96dpi），与原 PDF 一致，但字小
- 150 DPI = 1239×1752，缩放 100% 仍清晰，矢量渲染
- 300 DPI 太重，150 平衡清晰度与体积

### 4.3 为什么用 HTML + soffice 而非直接 PDFium？

- 译文要保持原文档的视觉风格（字体、字号、行高、缩进）— 这些由 soffice 处理
- 直接用 PDFium 文字 API 输出文本，丢失了 DOCX 的版式信息
- 走 HTML → PDF 链路：用户可读 HTML（soffice 渲染）→ 标准 PDF（PDFium 处理）

## 9. 已知约束

- soffice 启动开销大（~1.5s 冷启动），单页渲染不能低于 1.5s
- 长文档（100+ 页）用户滚到底部时才会触发对应页的渲染，等待 ~2s
- 后续可优化：预渲染前 3 页（用户进入就立即渲染首页 + 下一页）
- 并发去重仅在"同 key"生效；不同 key 完全独立（soffice 资源竞争仍可能发生，但概率小）
