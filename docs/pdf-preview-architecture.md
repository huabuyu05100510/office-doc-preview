# PDF/文档预览：顶尖架构方案

## 背景与问题

压测样本 `蘑菇书.pdf`（172MB / 189 页）暴露的核心性能问题：

- 第 10 页含一张 **7713×3817** 超大内嵌图（1646 ppi），被缩放显示到页面大小。
- pdf.js worker 解码 + 缩放该图要 **~15 秒**（p10 实测 15660ms）。
- 渲染过这类重页后 **worker 性能被拖垮**，后续页一并变慢（p11=6s, p12=10s）。
- 同样纯文字页 p130 首次渲染只要 **353ms** —— 所以不是"后面页都慢"，而是渲染过重页后 worker 被拖慢。
- 主线程内存仅 10MB，**不是泄漏**。

根因：**pdf.js 客户端现场栅格化**对超大内嵌图无能为力。线性化、虚拟化、可见页优先、dpr=1、page.cleanup() 都做了仍不够。

## 顶尖方案：服务端全量预处理 + 前端零计算

对标 Google Docs / 腾讯文档 / 飞书预览。核心是**三层解耦**（不是"图片 OR 文本"，而是三者并存）：

```
PDF 上传 → 服务端一次处理 → 产出三类资产（缓存到磁盘/CDN）
  ├─ 1. 每页 PNG/WebP（画布层）—— 预渲染好，浏览器直接 <img>
  ├─ 2. 每页文字 + 坐标 JSON（文本层）—— 独立导出，不依赖 pdf.js
  └─ 3. 文档级元数据（页数 / 尺寸 / 大纲 / 缩略图）

前端：
  ├─ <img> 显示画布层（虚拟滚动，<10ms 切页）
  ├─ 透明 <span> 叠文本层（可选中、可复制、可全文搜索）
  └─ 无需加载 pdf.js（省 1MB+，移动端尤其重要）
```

### 关键设计点（每个都是顶尖产品的做法）

1. **多分辨率瓦片**（Google Docs 做法）：大图页预渲染多个分辨率缩略图 + 高清，缩放时按需切换，避免一次性传大图。

2. **首屏渐进**：先出低清缩略图（KB 级，瞬间显示），高清异步替换，永不空白。

3. **按需渲染 + 持久缓存**：服务端不在上传时一次性渲染全部 189 页（慢），而是**首次访问某页才渲染、产物落盘**，二次访问直接命中缓存。

4. **WebP 而非 PNG**：体积小 30–50%，解码快，移动端省流量。

5. **文本层用 JSON**：用 `pdftotext -bbox-layout` 导出每页文字 + 精确 bbox 坐标，前端绝对定位透明 span。彻底脱离 pdf.js。

6. **可搜索 / 可标注**：文本 JSON 支持全文检索（Ctrl+F）；坐标支持后续画标注（标注功能天然契合这套——直接在图片层上叠加 annotation 坐标）。

7. **CDN + Range**：产物按页分文件，支持 Range + 缓存，移动端弱网也好。

8. **小文档降级**：纯文字小 PDF 仍可走 pdf.js（更省事），大 / 复杂 PDF 走图片化路线。按文档大小 + 复杂度自动选路。

### 直接兑现的诉求对照

| 诉求 | 本方案兑现 |
|------|-----------|
| 后面加载慢 | 图片按需加载，每页 <50ms 显示 |
| 闪动 | 渐进式高清替换，无白屏 |
| 复制 | 透明文本层，文字真实可复制 |
| 对标顶尖 | 即 Google / 腾讯 / 飞书的工程实现 |

## 已落地的基础设施（支撑本方案）

- **线性化**：`pdf-optimize.mjs`（qpdf `--linearize`），让 pdf.js / 按需 Range 顺序读取。
- **服务端栅格化**：`pdf-rasterize.mjs`（pdftoppm，已验证 p10 渲染 1.7s vs pdf.js 15s）。
- **soffice 转码池 + 高保真**：实例池、预热、FilterOptions、真实字体（Carlito / Noto CJK SC / 改名克隆）。
- **上传字节完整性**：`readBody` + `parseMultipart`（SHA256 验证）。
- **前端虚拟化 + 可见页优先**：PdfPreview，IntersectionObserver + 串行队列 + 回收。
